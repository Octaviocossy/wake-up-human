# Command: create-issue

Generate an issue from a requirement description. The issue body must contain a full
implementation plan following the structure in `.agents/rules/plan-creation.md`. In GitHub mode
it is a GitHub issue, adapted for GitHub Markdown (no YAML frontmatter, no
Status/Created/Updated lines). In local mode (`.agents/rules/local-mode.md`) it is a **local
issue**: a plan file under `.agents/plans/`, with the same body under a local-issue header.

## Context injected by the wrapper

The wrapper injects the output of `sh .agents/scripts/harness-mode.sh`, which is two lines:
- `Mode: github`, `Mode: local` or `Mode: refused`;
- `Remote: <origin URL>` or `Remote: (none)` — or, after `Mode: refused`, `Reason: <message>`.

In GitHub mode the command also reads `.agents/labels.md` — the label taxonomy it must pick
from in step 7. Local mode applies no labels and never reads it.

## Mode

Read the `Mode:` line before anything else:

- `Mode: refused` → write nothing. Relay the `Reason:` line to the user verbatim and stop.
- `Mode: github` → follow **Instructions — GitHub mode**.
- `Mode: local` → follow **Instructions — local mode**.

Then state the active mode to the user before writing anything (ADR-0023), e.g.
`Mode: github — creating a GitHub issue in <owner>/<repo>.` or
`Mode: local — writing a local issue under .agents/plans/; nothing leaves this machine.`

## Instructions — GitHub mode

When invoked with a requirement description (`$ARGUMENTS`):

1. **Read the requirement** from `$ARGUMENTS`. If empty, ask the user to provide one.
2. **Parse owner/repo** from the injected `Remote:` line (supports both HTTPS and SSH formats).
   If it reads `Remote: (none)`, stop: GitHub mode needs an `origin` remote. Tell the user to
   add one, or to set `USE_GITHUB=false` in `.agents/harness.config` for local mode.
3. **Check for duplicates** by calling `mcp__github__list_issues` with `state: "open"` and
   `per_page: 20`. If a near-identical issue exists, tell the user and stop (do not create a duplicate).
4. **Inspect relevant source files** using Read/Bash if needed to understand the codebase
   context required to produce accurate affected-files and step-by-step sections.
5. **Generate the issue title**: concise, action-oriented, ≤ 72 characters.
   - Use Conventional Commits style when appropriate: `feat: ...`, `fix: ...`, `chore: ...`
   - Examples: `feat: add contact form validation`, `fix: courses list empty state`
6. **Generate the issue body** using this exact structure:

   ```
   ## Goal
   One or two sentences: what is being built and why.

   ## Context
   - What exists today
   - What prompted this work
   - Constraints, deadlines, dependencies the implementer must know

   ## Affected Files
   | Action | File Path | Purpose |
   |--------|-----------|---------|
   | CREATE/MODIFY/DELETE | `path/from/root` | one-line purpose |

   ## Step-by-Step Implementation
   Numbered steps. Each step: what, where (full path), how (code snippets,
   function signatures, imports, patterns to follow), why (one sentence).

   ## Architecture Decisions
   Non-obvious choices: why this approach over alternatives, trade-offs, patterns referenced.

   ## Acceptance Criteria
   - [ ] Specific verifiable checks
   - [ ] Project acceptance commands pass (from `AGENTS.md` › Commands, or `ACCEPTANCE_CMD`
         in `.agents/harness.config`; e.g. `pnpm lint && pnpm build` for Node, or
         `xcodebuild -scheme <App> build` for Swift)
   - [ ] Manual smoke test steps if applicable

   ## Open Questions
   Anything unresolved needing input before or during implementation. If none, write "None."

   ---
   *Generated by `/create-issue`. Run `/planning <description>` when starting
   implementation to create a persisted plan in `.agents/plans/`.*
   ```

7. **Derive the labels** (read `.agents/labels.md` first; maximum 3, exactly one `type:`):
   - **`type:`** — the closed-facet value matching the Conventional Commits prefix of the title
     you just generated. Pick only from the `labels` block in `.agents/labels.md`. Step 5 makes
     that prefix optional ("when appropriate"), so when the title carries none, derive the value
     from the issue's own content instead — never skip `type:`, and never invent a value outside
     the block. Every issue gets exactly one.
   - **`area:`** — derived from the `## Affected Files` section you just wrote. **Reuse before
     invent:** run `gh label list --limit 200` and reuse an existing `area:` value when one
     covers the issue. Only when none does, create it first:
     `gh label create "area:NAME" --color ededed --description "ONE LINE"`.
   - **Best-effort.** If `gh` is unavailable, unauthenticated, or the create fails, carry on with
     whatever labels you have — including none — and say so in step 9. A label must never block
     the issue from being created.
8. **Create the issue** by calling `mcp__github__issue_write` (`method: "create"`) with `owner`,
   `repo`, `title`, `body`, and `labels` (omit `labels` entirely if step 7 produced none).
9. **Report** the created issue URL and the labels applied. If any label could not be applied,
   say which and why — the issue still exists.

## Instructions — local mode

No `mcp__github__*` tool, no `gh` command and no remote git command runs in this mode
(`.agents/rules/local-mode.md` › Nothing leaves the machine).

When invoked with a requirement description (`$ARGUMENTS`):

1. **Read the requirement** from `$ARGUMENTS`. If empty, ask the user to provide one.
2. **Check for duplicates** with `sh .agents/scripts/local-issues.sh list --open`. Each line is
   `<id>`, `<status>`, `<path>`, `<title>`, tab-separated. If a near-identical open local issue
   exists, tell the user its ID and path and stop (do not create a duplicate).
3. **Inspect relevant source files** exactly as GitHub-mode step 4.
4. **Generate the title** exactly as GitHub-mode step 5.
5. **Generate the body** with exactly the structure of GitHub-mode step 6 — Goal, Context,
   Affected Files, Step-by-Step Implementation, Architecture Decisions, Acceptance Criteria,
   Open Questions — ending with this footer instead of the GitHub one:

   ```
   ---
   *Generated by `/create-issue` in local mode. This file is the issue: check out
   `local-<n>-<slug>` and run `/execute-issue`.*
   ```

6. **Allocate the ID** with `sh .agents/scripts/local-issues.sh next-ids 1`, which prints
   `local-<n>`. Allocate now, immediately before writing — never at the start of the command.
7. **Derive the slug** from the title: drop a Conventional Commits prefix (`feat: `,
   `fix(scope): `, …), lowercase it, turn every run of characters outside `a-z0-9` into a single
   `-`, trim `-` from both ends, and cut it to at most 32 characters at a `-` boundary.
8. **Write the local issue** to `.agents/plans/<YYYY-MM-DD>-local-<n>-<slug>.md`, using today's
   date and never overwriting an existing file. The header comes first, then the body from
   step 5:

   ```
   # <title>

   > Issue: #local-<n>
   > Status: **draft**
   > Created: <YYYY-MM-DD>
   > Updated: <YYYY-MM-DD>

   ## Goal
   …
   ```

   Nothing follows the ID on the `> Issue:` line.
9. **Check the write** with `sh .agents/scripts/local-issues.sh find local-<n>`: it must print
   the path from step 8 and exit 0. On exit 2 another plan already claims the ID. Report both
   paths and stop; do not delete or renumber either file.
10. **Apply no labels.** Do not read `.agents/labels.md` and do not run `gh label`: a local issue
    has none.
11. **Do not commit** the plan file. The user commits plan files when they choose.
12. **Report** the path, the ID, and the next commands, and say that the plan file is
    uncommitted:

    ```
    git checkout -b local-<n>-<slug>
    /execute-issue
    ```

## Rules

- Be exhaustive in step details — another model will implement from the issue alone.
- Include actual code snippets for non-trivial logic.
- Reference existing files as implementation anchors ("follow the pattern in `src/adapters/courses.adapter.ts`").
- List every import a new file will need.
- Flag blockers (env vars, external actions, user decisions) explicitly.
- Never create a duplicate — check open issues first: `mcp__github__list_issues` in GitHub mode, `sh .agents/scripts/local-issues.sh list --open` in local mode.
- In GitHub mode: maximum 3 labels, exactly one `type:`. Reuse an existing `area:` before inventing one.
- Labels are informational — never assume anything downstream reads them (ADR-0015).
- State the mode before writing anything; on `Mode: refused`, write nothing and relay the reason.
- In local mode: no `mcp__github__*` tool, no `gh` command, no remote git command, no labels;
  nothing follows the ID on the `> Issue:` line; never commit the plan file.
