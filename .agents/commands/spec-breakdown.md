# Command: spec-breakdown

Decompose a large specification into a parent **epic** plus N child issues (each a full
implementation plan), with a dependency graph persisted in an epic plan file. In GitHub mode the
epic and its children are GitHub issues. In local mode (`USE_GITHUB=false` in
`.agents/harness.config`, ADR-0023) they are **local issues**, plan files under
`.agents/plans/` identified `local-<n>`, and nothing leaves the machine. After this command
completes, run `/execute-epic` to execute the children in parallel.

## Context injected by the wrapper

- **Harness mode**: the injected `sh .agents/scripts/harness-mode.sh` output. Its first
  line is `Mode: github`, `Mode: local` or `Mode: refused`. Its second line is
  `Remote: <url>`, `Remote: (none)`, or `Reason: <message>` when refused. Step 0 acts on it.
- **Spec** — `$ARGUMENTS` is either a path to a spec file (read it) or the spec text
  directly; if empty, ask the user to provide one.

In GitHub mode the command also reads `.agents/labels.md`, the label taxonomy the epic and every child must pick from (steps 5 and 6). Local mode has no labels.

## Instructions

### 0 — State the mode

Read the injected `Mode:` line. If the context has none, because a caller such as `/spec`
still injects only `git remote get-url origin`, run `sh .agents/scripts/harness-mode.sh`
yourself and use its output.

- `Mode: refused`: stop. Relay the `Reason:` line verbatim and write nothing.
- `Mode: github`: follow steps 1–9.
- `Mode: local`: follow step 1, then the **Local mode** section below, in place of steps 2–9.

Name the mode in your first message, before anything is created or written (ADR-0023).

### 1 — Ingest the spec

If `$ARGUMENTS` is a path that exists in the working tree, read it. Otherwise treat
`$ARGUMENTS` as the spec text itself. If `$ARGUMENTS` is empty, ask the user to
supply a spec file path or description and stop until they do.

**Settled design specs.** If the path is under `.agents/specs/` and its header says
`Status: **settled**`, it is the output of a `/grill` session
(`.agents/rules/design-interrogation.md`). Treat its `## Settled Decisions` and
`## Explicitly Out of Scope` sections as **authoritative** — do not re-litigate a decision
already recorded there, and do not slice work the spec explicitly excluded. Carry the relevant
decisions and their rationale into each child issue's `## Architecture Decisions`, and copy any
entries under `## ADRs Raised` into the epic body so the epic references them.

### 2 — Parse owner/repo

Extract `owner` and `repo` from the injected `Remote:` line. Supports both HTTPS
(`https://github.com/<owner>/<repo>.git`) and SSH (`git@github.com:<owner>/<repo>.git`).

If it reads `Remote: (none)`, stop: GitHub mode needs an `origin` remote. To break the spec
down without GitHub, set `USE_GITHUB=false` in `.agents/harness.config`.

### 3 — Duplicate guard

Call `mcp__github__list_issues { state:"open", per_page:20 }`. If an issue with a
matching epic title already exists, stop and point the user at `/execute-epic #<n>`.
Do not create a duplicate.

### 4 — Decompose into 3–8 vertical slices

Apply the heuristics in `.agents/rules/parallel-orchestration.md` (Decomposition
Heuristics section):

- **Foundation-first:** isolate a buildable-skeleton slice (project/app target, shared
  types, CI scaffold) as the dependency root so siblings only *add* files.
- **Data-before-UI:** model/persistence slices before their UI consumers.
- **Independent behaviors:** each slice implements one complete user-observable behavior,
  not a horizontal layer.

If the spec yields fewer than 3 slices, tell the user to use `/create-issue` instead.
If it yields more than `MAX_CHILDREN` (default 12), ask the user to coarsen the spec
before proceeding.

Assign a branch name per child: `<placeholder#>-<kebab-title>` (use sequential
placeholder numbers; update to real numbers in step 7).

### 5 — Create the epic issue

Call `mcp__github__issue_write` (`method: "create"`) with `owner`, `repo`, `labels`, and the
title/body below. The epic's labels are `type:epic` plus at most one `area:` covering the epic
as a whole — same derivation and same best-effort handling as `/create-issue` step 7.

```
title: "epic: <short title>"
body:
  ## Epic: <title>
  <1–2 sentence goal>

  ### Children
  - [ ] #<TBD-a> feat: <slice a>
  - [ ] #<TBD-b> feat: <slice b>

  ### Dependency graph
  ```waves
  # wave : issues
  1 : <TBD-a>
  2 : <TBD-b> <TBD-c>
  # edges (child -> depends-on)
  <TBD-b> -> <TBD-a>
  <TBD-c> -> <TBD-a>
  ```
  ---
  *Generated by `/spec-breakdown`. Tracking issue — do not implement here. Run `/execute-epic`.*
```

Record the created epic issue number as `<epic>`.

### 6 — Create each child issue

For each slice, call `mcp__github__issue_write` (`method: "create"`) with `owner`, `repo`,
`title`, `body`, and `labels` — the child's own labels, derived per the **Labels** paragraph
below (omit `labels` entirely if none were derived). The body must follow the full
`/create-issue` house style (Goal, Context, Affected Files, Step-by-Step Implementation,
Architecture Decisions, Acceptance Criteria, Open Questions), with two additional header
lines prepended:

```
> Epic: #<epic>
> Depends on: #<a>, #<b>
```

(Omit `> Depends on:` for the foundation slice or any child with no dependencies.)

**Labels.** Label every child from **its own** `## Affected Files`, exactly as `/create-issue`
step 7 does — maximum 3, exactly one `type:`, reusing an existing `area:` before inventing one.
A child **never inherits the epic's labels**: propagating them would give every child an
identical set and destroy the filter's value. The `> Epic: #N` header is what groups them.

**Acceptance Criteria** must use the project's actual acceptance commands from
`AGENTS.md` › Commands (e.g. `xcodebuild -scheme KeyCount build` for a Swift project,
or `pnpm lint && pnpm build` for a Node project). Do **not** hardcode `pnpm` for a
non-Node project.

Record each created child's real issue number and branch name
(`<issue#>-<kebab-title>`).

### 7 — Second pass: update the epic

Call `mcp__github__issue_write` (`method: "update"`) to rewrite the epic body, substituting all `<TBD-*>`
placeholders with the real issue numbers from step 6 (task-list + `waves` block).
Preserve the rest of the body verbatim.

### 8 — Persist the epic plan

Write `.agents/plans/[yyyy-mm-dd]-epic-<slug>.md` using this template:

```markdown
# Plan: Epic — <title>

> Status: **draft**
> Created: [YYYY-MM-DD]
> Issue: #<epic>
> Integration branch: epic/<epic>-<slug>

## Goal
<1–2 sentences>

## Children & Waves

| Wave | Issue | Branch | Title | Status |
|------|-------|--------|-------|--------|
| 1 | #<a> | `<a>-<slug>` | <title> | pending |
| 2 | #<b> | `<b>-<slug>` | <title> | pending |

## Dependency Edges

```
<b> -> <a>
<c> -> <a>
```
```

### 9 — Report

Respond with:
- Epic issue URL and number
- The integration branch name (`epic/<epic>-<slug>`) that `/execute-epic` will create
  and auto-merge each wave's children into
- Each child issue URL, number, branch, and assigned wave
- The labels applied to the epic and to each child. If any label could not be applied, say
  which and why — the issues still exist, since labelling is best-effort.
- The computed waves table
- A reminder to run `/execute-epic` (or `/spec` if this was called stand-alone)

## Local mode (`USE_GITHUB=false`)

Followed in place of steps 2–9 when step 0 reads `Mode: local`. The epic and its children are
**local issues**, plan files in the formats of `.agents/rules/local-mode.md` › Local epics.
Nothing leaves the machine: no `mcp__github__*` call, no `gh` call, and no `git fetch`,
`git push` or `git ls-remote`. Nothing is committed and no branch is created. The user commits
the plan files when they choose, and the runner creates the integration branch at
`/execute-epic` time. Step 1 (ingest, including the settled-spec rules) and the decomposition
rules of step 4 apply unchanged.

### L2 — No owner/repo

There is no repository to address. Ignore the `Remote:` line. `Remote: (none)` is fine here.

### L3 — Duplicate guard

Derive the epic title from the spec: `epic: <short title>`, the same title step 5 would give a
GitHub epic issue. Run `sh .agents/scripts/local-issues.sh list --epics --open`. It prints one
tab-separated line per open local epic: `<id>`, `<status>`, `<path>`, `<title>`. Compare each
`<title>` with yours case-insensitively, after stripping a leading `epic:` and the surrounding
whitespace from both. On a match, stop and write nothing: name that epic's ID, status and path,
and point the user at `/execute-epic <id>`.

### L4 — Decompose and compute the waves

Decompose exactly as step 4, with the same heuristics and the same stops for fewer than 3
slices or more than `MAX_CHILDREN`. Name the slices `S1`, `S2`, … in decomposition order
instead of assigning branch names, and record each dependency as an edge `Sx -> Sy`. Compute
the waves with Kahn leveling (`parallel-orchestration.md` › Wave / Frontier Algorithm),
including the cycle guard.

### L5 — Allocate the IDs

Order the slices by wave, then by decomposition order within a wave. Run
`sh .agents/scripts/local-issues.sh next-ids <k>`, where `<k>` is 1 + the number of slices.
It prints `<k>` consecutive fresh IDs, one per line.

- The **first** ID is the epic's.
- The rest go to the slices in the order just fixed, so every dependency carries a smaller ID
  than its dependents and each wave reads in ascending ID order.

Never compute an ID yourself. The script is the only allocator. From here on, use the IDs in
place of `S1…Sk` everywhere.

For each title, `<slug>` is the title without its Conventional-Commits prefix (`epic:`,
`feat:`, …), lowercased. Collapse every run of characters outside `[a-z0-9]` into one `-`,
strip any leading or trailing `-`, and cut at a `-` boundary to at most 30 characters.
`<yyyy-mm-dd>` is today's date.

| | Epic | Child |
|---|---|---|
| Plan file | `.agents/plans/<yyyy-mm-dd>-epic-local-<n>-<slug>.md` | `.agents/plans/<yyyy-mm-dd>-local-<n>-<slug>.md` |
| Branch | `epic/local-<n>-<slug>` (the integration branch) | `local-<n>-<slug>` |

If any of these plan files already exists, stop, name it, and write nothing.

### L6 — Write the child plan files

Write one file per slice in the child format of `.agents/rules/local-mode.md` › Local epics.

- **Header:** `# <title>`, then `> Issue: #local-<n>` with nothing after the ID,
  `> Status: **draft**`, and `> Created:` and `> Updated:`, both today. Then
  `> Epic: #local-<epic>` and `> Depends on: #local-<a>, #local-<b>`. Omit the
  `> Depends on:` line for a slice with no dependency.
- **Body:** the full `/create-issue` house style, as step 6 describes it: Goal, Context,
  Affected Files, Step-by-Step Implementation, Architecture Decisions, Acceptance Criteria
  (with the project's own acceptance commands), and Open Questions. A settled spec's decisions
  carry into each child's `## Architecture Decisions`, as step 1 says.
- **Footer:** the footer line from the template.

Local mode has no labels.

### L7 — Write the epic plan file

Use the epic format of `.agents/rules/local-mode.md` › Local epics:

- the header, including `> Integration branch: epic/local-<n>-<slug>`;
- `## Goal`, naming the spec file when the input was one;
- `## Children & Waves`, with every child's Status `pending`;
- `## Dependency Edges`;
- `## ADRs Raised`, only when the input was a settled spec with entries under its
  `## ADRs Raised`. Copy those entries verbatim.

Every ID is already known, so there is no second pass. Step 7 has no local counterpart.

### L8 — Check what was written

- For the epic and every child, run `sh .agents/scripts/local-issues.sh find local-<n>`. Each
  must print exactly the path you wrote and exit 0.
- Run `sh .agents/scripts/local-issues.sh list --epics`. The new epic must appear with status
  `draft`.

A failure means a header deviates from the format. Fix that header in place and check again.
Never delete or renumber a file.

### L9 — Report

Respond with:
- `Mode: local`, and that nothing was sent to GitHub or to any remote
- The epic's ID and plan-file path
- The integration branch `epic/local-<n>-<slug>`. `/execute-epic` creates it from the local
  `BASE_BRANCH`, and no command pushes it: that is the user's call
- Each child's ID, plan-file path, branch and wave
- The computed waves table
- That the plan files are uncommitted and are the user's to commit
- A reminder to run `/execute-epic local-<n>` (or `/supervise-epic local-<n>`), or, when
  `/spec` called this command, to continue to its Phase 2

## Rules

- Follow `parallel-orchestration.md` for all decomposition and naming decisions.
- Follow `plan-creation.md` for the epic plan file format in GitHub mode, and `local-mode.md` › Local epics for every file local mode writes.
- Never create a duplicate. Check open issues first (step 3) or the local epics (L3).
- Use project-derived acceptance commands in child issues, not hardcoded `pnpm`.
- If fewer than 3 slices result, stop and recommend `/create-issue` instead.
- Label the epic `type:epic`; label each child from its own content, never by inheritance. (GitHub mode; local mode has no labels.)
- State the mode before writing anything, and stop on `Mode: refused` (step 0).
- In local mode, make no GitHub call and run no remote command. IDs come only from `local-issues.sh next-ids`. Never commit the plan files and never create a branch.
